# eliotjang-dungeon-server — 기술 문서

> Linux C++20 게임 서버 — raw epoll 네트워크 코어를 시스템콜 레벨부터 직접 구현  
> 작성: 장성원 (eliotjang2@gmail.com) | 리포: https://github.com/eliotjang/eliotjang-dungeon-server  
> 본 프로젝트는 단계적으로 개발 중이며, 이 문서는 **1단계(네트워크 코어) 완료 시점**의 제출본입니다. 구현 완료 범위와 설계 단계 범위를 명확히 구분해 서술했습니다.

## 1. 이 프로젝트가 증명하려는 것

던전앤파이터와 같은 채널 기반 온라인 게임 서버의 요체를, 프레임워크 없이 시스템콜 레벨부터 직접 구현하는 프로젝트입니다.  
실무에서는 Boost.Asio 기반 사내 엔진 위에서 개발했기에, 그 엔진이 추상화하던 계층 — 소켓, 이벤트 루프, 버퍼, 프레이밍 — 을 직접 만들어 이해를 증명하는 것이 목표입니다.

**요건 매핑 (구현/설계 구분):**

| 영역 | 상태 | 내용 | 코드/테스트 |
|---|---|---|---|
| 네트워크 (소켓) | ✅ 구현 | raw epoll(LT) 리액터, non-blocking 소켓, 세션 수명 관리, 링버퍼, 길이 프리픽스 프레이밍, 악성 입력 방어 | `src/net/` 전체, GTest 11종 |
| 비동기 (이벤트 기반 I/O) | ✅ 구현 | 단일 IO 스레드가 epoll 이벤트 루프로 수만 동접 처리 (동접 약 2만8천 세션 실측 — §6) | `epoll_reactor.cc` |
| 디버깅·이슈 추적 | ✅ 실사례 | 트러블슈팅 2건 기록 | — |

- 구현 예정: 비동기 (멀티스레드 파이프라인) / 데이터베이스

## 2. 빌드 및 실행 (Linux / WSL2, 5분 재현)

요구: gcc 13+, cmake 3.21+, ninja, docker (MySQL 환경용 — 현 단계 서버 구동에는 불필요)

```bash
cmake --preset debug && cmake --build --preset debug   # 빌드
ctest --preset debug                                    # 단위 테스트 12종
./build/debug/ejd_server &                              # 서버 (포트 5555)
./build/debug/ejd_bot 500                               # 봇 500세션 에코 검증 → "ok: 500"
docker compose up -d                                    # MySQL 8.4 (스키마 자동 시드)
```

## 3. 아키텍처 (현재 구현)

```
[봇/클라이언트 N] ──TCP──> [IO 스레드: epoll_wait 이벤트 루프]
                             ├─ 리슨 fd 이벤트 → accept4 루프(EAGAIN까지, SOCK_NONBLOCK)
                             │    → Session 생성(RAII) → epoll 등록 → 세션 맵 소유
                             └─ 세션 fd 이벤트 → Session::OnReadable()
                                  ① read 루프(EAGAIN까지) → 수신 링버퍼 축적
                                  ② 프레이밍: 완성 패킷 추출 → 검증 → 처리(에코)
                                  종료/에러/악성 → 세션 정리(epoll DEL → 맵 erase → fd close)
```

- **소유권 구조**: 리액터가 `unordered_map<int, unique_ptr<Session>>`으로 세션을 단독 소유하고, 세션은 `UniqueFd`(자체 RAII 래퍼)로 fd를 단독 소유. 모든 자원 해제가 소멸자 체인으로 보장되어 fd 누수가 구조적으로 불가능 (봇 1만 세션 접속·종료 반복 후 fd 개수 불변 확인)
- **프로토콜**: `[uint32 length][uint16 msg_id][uint16 flags]` 8바이트 헤더(pack(1), static_assert로 고정) + 페이로드. length는 헤더 포함 전체 길이, 리틀엔디안 — 클라·서버를 모두 통제하는 환경에서 변환 비용을 제거하는 선택이며, 표준 네트워크 오더(빅엔디안)와의 트레이드오프를 인지한 결정

## 4. 핵심 구현과 설계 결정

### 4.1 UniqueFd — fd 소유권의 타입화
`unique_ptr`의 소유권 의미론을 fd에 직접 구현한 RAII 래퍼 (복사 금지, 이동 = 소유권 이전, 소멸 = close).  
이동 대입 시 기존 fd를 먼저 정리해 누수를 차단하고, close의 EINTR은 재시도하지 않습니다

### 4.2 epoll 레벨 트리거(LT) 선택
ET(엣지 트리거)는 wakeup 횟수를 줄이는 최적화지만, EAGAIN까지 완전 소진하지 못하면 이벤트가 영원히 오지 않는 정확성 리스크가 있습니다.  
최적화보다 정확성을 우선해 LT를 선택했고, ET 전환은 병목이 측정으로 확인될 때의 개선 항목으로 남겼습니다.

### 4.3 이벤트 식별: data.fd + 세션 맵 조회
epoll_event의 data에 세션 포인터 대신 fd를 넣고 매 이벤트마다 맵을 조회합니다.  
같은 epoll_wait 배치에 한 세션의 이벤트가 2개 도착한 경우(예: EPOLLIN|EPOLLHUP), 첫 이벤트 처리에서 세션이 삭제되면 포인터 방식은 dangling 접근이 됩니다.  
맵 조회 방식은 삭제된 fd의 잔여 이벤트가 조회 실패로 자연히 무시되어, 수명 버그를 자료구조 선택으로 차단합니다.

### 4.4 링버퍼 — 소비 O(1)의 수신 버퍼
고정 용량(세션당 64KB = 최대 패킷 4KB의 16배, 목표 동접 × 버퍼가 메모리 예산 내) 순환 버퍼.  
head와 size만 상태로 유지하고 tail은 유도해(상태 최소화) full/empty 모호성을 제거했습니다.  
경계 memcpy로 처리하며, 경계 케이스는 단위 테스트로 고정했습니다.

### 4.5 프레이밍 — 악성 입력을 먼저 거른다
완성 패킷 추출 시 검증 순서가 핵심입니다: **length 검증(최소·최대)을 본문 대기보다 먼저** 수행합니다.  
순서가 반대면 length=4GB짜리 악성 헤더를 "본문 수신 중"으로 취급해 자원을 잡은 채 기다리게 됩니다.  
검증 실패는 즉시 킥, 수신 버퍼 상한 초과(폭주 클라이언트)도 킥

### 4.6 블로킹 / 논블로킹
"스트림에서 메시지 복원"을 봇(블로킹)은 ReadExact 순차 코드로, 서버(논블로킹)는 링버퍼 상태 보존 + 이벤트 재개로 풉니다.  
두 방식을 같은 프로토콜 위에 구현했습니다.

## 5. 검증

- **단위 테스트 12종** (GTest): 소켓 없이 순수 로직으로 검증 가능하도록 계층을 분리한 설계의 결과물
  * 링버퍼 경계(랩어라운드 쓰기/읽기, 가득 참 거부, 계약 위반 DeathTest)
  * 프레이밍(1바이트씩 수신, 3연속 패킷 순서, 악성 length 2종, 랩 경계에 걸친 헤더)
- **봇 클라이언트 검증**: 연결마다 고유 메시지를 보내 응답 내용 비교
  * 세션 간 데이터 섞임(격리 실패)을 잡는 설계
  * 500·10,000세션 에코 검증 통과
  * 접속·종료 반복 후 fd 누수 없음

## 6. 실측과 트러블슈팅

### 6.1 동접 측정
10만 세션 목표로 부하를 걸자 약 2만8천 세션에서 봇의 connect가 `EADDRNOTAVAIL`로 실패했습니다. 분석: TCP 연결의 신원은 4-튜플이고, 단일 클라이언트 IP에서 같은 서버로의 동시 연결 수는 임시 포트 범위(`ip_local_port_range` = 32768~60999, 28,232개)가 상한입니다. 즉 **병목은 서버가 아니라 부하 생성기 쪽**이었고, 서버는 단일 IO 스레드로 동접 약 2만8천 세션을 유지했습니다(서버 측 한계는 fd 한도와 메모리). 실측 수치보다, 실패 지점에서 OS 계층으로 원인 확인

### 6.2 "연결만 되고 응답이 없음"
프레이밍 전환 직후 봇이 응답 대기에서 무한 블록되는 증상이 발생했습니다. 접속 로그는 정상 → 서버가 에코를 안 보냄 → OnReadable 흐름 추적 → read 루프의 EAGAIN 분기처리가 잘못되어 **추출·응답 단계가 도달 불가능 코드**였음을 확인. 컴파일러는 이런 결함을 경고하지 않으므로(도달 불가 경고는 기본 비활성), 계층별 로그와 흐름 추적으로만 잡을 수 있는 유형이었습니다.

### 6.3 SO_REUSEADDR가 못 뚫는 것
디버깅 중 `bind: Address already in use`가 SO_REUSEADDR 설정해놔도 발생  
원인은 디버거에 정지된 이전 서버 프로세스가 포트를 점유한 것. SO_REUSEADDR는 TIME_WAIT(죽은 연결의 잔재)만 허용하며, **살아있는 리스너는 여전히 차단**된다는 것(포트 하이재킹 방지)을 실전으로 확인했습니다.

## 7. 설계 완료 — 구현 로드맵

다음 단계는 설계를 마치고 구현을 진행 중입니다.  
채널 단위 격리 구조에서 진행

### 7.1 채널 샤딩 스레드 모델
채널 각각을 N개 로직 스레드 중 하나에 고정 배정(샤딩)합니다.  
한 채널의 로직은 항상 같은 스레드에서만 실행되므로 채널 내부는 락 없는 직렬 실행이 보장되며, 락은 IO 스레드와 샤드 스레드의 경계(MPSC 큐, mutex 기반) 한 곳에만 존재합니다.

### 7.2 DB 계층
- 접근 구조: 게임 로직은 DB에 직접 붙지 않고 **DB 워커 스레드에 요청을 위임** (요청에 세션 세대 ID를 동봉)
- 안전장치: 커넥션·트랜잭션 RAII(미커밋 시 소멸자 롤백), 데드락(1213) 재시도, 재연결 지수 백오프
- **세대 ID 마샬링**: DB 응답이 돌아온 시점에 세션이 이미 끊겼을 수 있으므로, 요청 시점의 세대 ID와 대조해 불일치면 응답을 폐기 — 비동기 콜백의 수명 문제를 프로토콜로 해결
- 시나리오: 로그인(계정 조회) / 던전 클리어 정산 — 골드·경험치·기록을 단일 트랜잭션으로, `SELECT ... FOR UPDATE` 행 잠금과 action_id 유니크 제약으로 중복 지급 방지(재시도 안전 = 멱등)

### 7.3 송신 큐
현재 write EAGAIN은 의도적 임시 처리(드롭+로그)입니다. 세션별 송신 버퍼 + EPOLLOUT 동적 등록/해제 + 송신 상한(백프레셔)으로 대체 예정입니다.

## 8. 실무 경험과의 관계

전 직장(모바일 소셜 MMO 2종)에서는 리드가 설계한 Boost.Asio 기반 사내 엔진 위에서 콘텐츠·DB·인프라를 개발했습니다 — 채팅·우편·선물 등 콘텐츠 수직 구현, DB 마이그레이션 파이프라인 구축, 대규모 GTest 문화가 저의 영역이고, 엔진 코어는 사용자이자 분석자였습니다. 본 프로젝트는 그 엔진이 추상화하던 계층을 밑바닥부터 다시 만들어 이해를 증명하는 작업이며, **전 직장 코드는 참조하지 않고** 공개 자료와 원리로부터 다시 구현했습니다.
